### The short version

The rules engine is in good shape: level-by-level resolution, an independent checker, parity gates and 10,000-character
runs are more than most builders have. The weak side is everything around it:

1. **Saved data can be lost or look lost** (section 1). This is the most important block. A character's last edit is
   dropped when another character is opened within 0.8 s; a failed save is never shown; a database error shows an
   empty library; backups live in the same database as the characters; there is no error boundary.
2. **Play-state bookkeeping has rules bugs** (section 2): Pact Magic and spell slots share one counter, long rests
   follow the 2014 hit dice rule for 2024 characters, three different "long rest" buttons do three different things,
   hit dice are one pool for multiclass characters.
3. **No linter, no formatter, CI runs none of the content gates** (section 4). The real gates run only on Chris's
   machine. `public/srd` is in the repository now, so CI can run them.
4. **A few files carry too much** (section 5): one function of about 890 lines in the importer, a 1,370-line
   component, lines of 300 to 500 characters throughout.

## 1. Data safety (do this phase first, in this order)

### S1. The last edit is lost when another character is opened quickly. Confirmed.

**Done 2026-11-10** (src/ui/saveQueue.ts and its test; checked in the browser with Chris's library: an edit followed at once by opening another character is in the library. Left open: the desktop window's close request (the copy in localStorage covers a quit, except for a character too big for it; see E6).)

`src/ui/App.tsx`, the autosave effect (about lines 140 to 165). Each run of the effect starts with
`window.clearTimeout(saveTimer.current)`. The save itself is a timer of 800 ms. `open()` sets a new id and character,
the effect runs again, and the timer that held the previous character's save is cleared. The previous character's
last edit is then in no store: `localStorage` was overwritten with the new character too. The same happens with New,
Random, an import and a restore.

Fix:
1. New file `src/ui/saveQueue.ts`, no React: a class `SaveQueue` with `schedule(id, character, summary)`,
   `flush(): Promise<void>` and `state: "saved" | "pending" | "saving" | "failed"` plus a `subscribe`. It holds at
   most one pending record. `schedule` for a *different* id than the pending one flushes the pending one at once,
   then schedules the new one. `flush` writes with `saveCharacterRecord` and keeps the record as pending when the
   write fails.
2. `App.tsx` uses it instead of the timer. `open()` calls `queue.flush()` before switching.
3. Flush on `visibilitychange` (hidden), on `pagehide`, and in the desktop app on the window's close request
   (`getCurrentWindow().onCloseRequested`: flush, then let it close; needs `core:window:allow-close` checked in
   capabilities).
4. Compare by reference, not by JSON text: the state is immutable, so `lastSavedRef === character` says "no edit".
   Today the whole character, portrait included, is turned into JSON twice on every change.

Tests (`src/ui/saveQueue.test.ts`, fake timers, fake-indexeddb): edit A then schedule B within 800 ms, A's edit is
stored; a failing store leaves state "failed" and a later flush retries; no write when nothing changed.

### S2. A failed save is invisible. Confirmed.

**Done 2026-11-10** (the bar shows Saved, Saving... or Not saved with Try again; the failure is logged. The e2e case is not written.)

`App.tsx`: `saveCharacterRecord(...).catch(() => {})`, and the action bar always shows "✓ Saved". If the database
is full or broken the player works on, sees "Saved", and loses everything at the next start.

Fix: the "Saved" mark reads `SaveQueue.state`: "Saved", "Saving...", or a red "Not saved" with a tooltip and two
buttons, Try again and Export this character (the existing JSON export). Log the error with `logEvent("save", ...)`.
e2e test: make `indexedDB.open` fail in the page, edit, expect "Not saved".

### S3. A database error shows an empty library. Confirmed.

**Done 2026-11-10** (listCharacters throws; Home says the library could not be read and keeps the last list; a restore stops. Test in backup.test.ts. listTemplates still returns an empty list on an error: to do.)

`src/aurora/storage.ts`: `listCharacters()` and `listTemplates()` catch every error and return `[]`. Home then shows
no characters, which reads as "my characters are gone". Worse, `restoreBackup(file, "merge")` in
`src/aurora/backup.ts` builds its "what is here" map from `listCharacters()`: when that read fails, every character
in the backup counts as new and **overwrites a newer copy** that is actually in the database.

Fix: `listCharacters()` throws. Add `listCharactersSafe(): Promise<{ ok: true; list } | { ok: false; error }>` for
the screens. Home shows "Your library could not be read" with the error and a Try again button, never the empty
state. `restoreBackup` uses the throwing version and aborts with a message. Go through every caller
(`grep -rn "listCharacters\|listTemplates" src`) and decide for each: show the error, or abort.

### S4. A new database connection on every call. Confirmed.

**Done 2026-11-10** (one connection per session, let go on a version change or close; a blocked upgrade says so.)

`storage.ts` `openDb()` runs `indexedDB.open` for every read and write and never closes the result. There is no
`onversionchange` handler, so a second window (the test app before D1 shared this store, two browser tabs today)
blocks an upgrade forever, and no `onblocked`.

Fix: one memoized `Promise<IDBDatabase>`; `db.onversionchange = () => { db.close(); cached = undefined; }`;
`db.onclose = () => { cached = undefined; }`; `req.onblocked` rejects with a readable message. Keep the
`VersionError` fallback as it is. Test with fake-indexeddb: 100 reads open the database once; after a simulated
version change the next read reopens.

### S5. Backups share the characters' fate. Confirmed.

**Done 2026-11-10** (parts 1 to 3: the daily backup is also a file in the app data folder's backups (14 kept, src/diskBackup.ts, three appdata capabilities), Settings shows the folder, the date is local, storage persistence is asked for. Part 4 (a backup before a replace restore, the D7 move and a new version's first start) is open.)

`backup.ts`: the daily backup is a string in the `backups` store of the same IndexedDB database. If WebKit drops or
corrupts the database (it has happened to WebKit apps after OS updates), the backups go with it. The date is UTC
(`toISOString`), so a backup made at 00:30 in Slovakia is filed under yesterday.

Fix:
1. Desktop: also write each daily backup to disk, `<app data>/backups/soul-forge-YYYY-MM-DD.json`, keep 14. Add
   the capabilities `fs:allow-appdata-read-recursive`, `fs:allow-appdata-write-recursive`,
   `fs:allow-appdata-meta-recursive` (the app log folder already has the same three). Settings shows the folder with
   an "Open folder" button (opener plugin) and lists disk backups for Restore.
2. Use the local date.
3. Call `navigator.storage.persist()` once at start and log the answer.
4. Make a disk backup automatically before: a restore in "replace" mode, the D7 migration, and the first start of a
   new version (compare `APP_VERSION` with a stored last version).

Test: `backup.test.ts` with an injected writer; the date function with a fixed clock in a +01:00 zone.

### S6. Any JSON is accepted as a character. Confirmed.

**Done 2026-11-10** (sanitizeCharacter in character.ts, normalizeCharacter calls it; sanitize.test.ts: 2,000 damaged characters read, resolve and build a sheet on the SRD content. Opening a file on Home names what was put right.)

`character.ts` `normalizeCharacter` spreads the raw object over a new character. A file with `"options": null`,
`"classes": "Fighter"`, a level of 500 or `"selections": []` passes and crashes later inside `resolve` or a screen
(for example `ch.options.includes`). A `version` higher than 2 is stamped back to 2 without a word.

Fix: `sanitizeCharacter(raw: unknown): { character: Character; repaired: string[] }` in a new
`src/aurora/sanitize.ts`. Field by field: wrong type becomes the default and is named in `repaired`; class levels are
whole numbers 1 to 20 and the total is capped at 20; `selections` is a record of string arrays; inventory entries get
a `uid` when missing and a quantity of at least 0; numbers that are `NaN` become defaults; unknown keys are kept (a
newer version's fields must survive an older build). A `version` above 2 throws "made by a newer Soul Forge". Use it at
every door: `loadCurrent`, library open, restore, imports, the test tools. `normalizeCharacter` stays as a thin call
to it so nothing else changes.

Test: a property test in `sanitize.test.ts`: 2,000 objects built by randomly breaking a valid character (delete a
key, swap a type, insert null) never make `sanitizeCharacter` or `resolve` throw on the SRD content.

### S7. No error boundary. Confirmed.

**Done 2026-11-10** (src/ui/ErrorBoundary.tsx around the app and around each screen; the whole-app one can start without the open character. The e2e case is not written.)

load a character whose species id points at an element with a deliberately broken rule (test content), expect the
fallback and a working Home.

### S8. Two running copies write over each other. Verify first.

Nothing stops two windows of the desktop app, or two browser tabs. Both autosave the same "current character" key and

## 2. Rules and play-state bugs

### R1. Pact Magic slots and spell slots share one counter. Confirmed.

**Done 2026-11-10** (`PlayState.pactUsed`, read and written through src/aurora/rest.ts; the sheet's pact row carries `pact: true`. An older single-class Warlock keeps its count; with ordinary slots of the same level an older count stays with those.)

`PlayState.slotsUsed` is keyed by spell level only. `sheet.ts` `buildCasting` gives a Warlock's pact row and a
Wizard's row `used: ch.play.slotsUsed[String(n)]`. A Warlock 3 / Wizard 3 has pact slots and wizard slots of 2nd
level: spending one marks both, and `PlayTab.tsx` `shortRest` deletes the level-2 count, which also returns the
Wizard's slots.

Fix: `PlayState.pactUsed?: number`. The pact line reads and writes it; `slotsUsed` is only the shared table. The
short rest resets `pactUsed`; the long rest resets both. `sanitizeCharacter` leaves old saves alone (single-class
Warlocks: move their one used count to `pactUsed` when the character has a pact line and no other slots; that needs
the registry, so do it in a small `upgradePlayState(ch, sheet)` called where `withGrantedItems` is called). Check
PlayTab line 490 (casting a spell spends `slotsUsed[level]`): it must spend from the line the spell is cast with.
Tests: `src/aurora/rest.test.ts`, Warlock 3 / Wizard 3.

### R2. Three long rests, three results; 2024 hit dice wrong. Confirmed.

**Done 2026-11-10** (src/aurora/rest.ts `shortRest`, `longRest(ch, sheet, rules)`: Play and Export call the same one, the Magic tab's button returns both kinds of slot; the first class's edition decides the hit dice. Open: features that return one use on a short rest are still fully reset, and Plutonium's table is not written up.)

- `PlayTab.tsx` `longRest`: hit points, slots, feature uses, resources, exhaustion minus 1, **half** the hit dice
  back.
- `SheetTab.tsx` line 92 "Long rest": **all** hit dice back, resources and exhaustion untouched, wild shape kept.
- `MagicTab.tsx` line 32: slots only.

The 2024 rules give back all spent hit dice on a long rest; the 2014 rules give back half the total (at least one).
PlayTab applies the 2014 rule to everyone.

Fix: `src/aurora/rest.ts` with pure `shortRest(ch, sheet)` and `longRest(ch, sheet, edition)`; edition from the
first class's `edition` stamp. All three buttons call it. Check Plutonium and the two rule books for what a short
rest returns, and write the table of what each rest resets into docs/PLUTONIUM.md. Also check: `shortRest` finds
short-rest features by the words "short rest" in the usage text; the 2024 features that return *one* use on a short
rest ("regain one expended use when you finish a Short Rest") are fully reset by this. Test each case.

### R3. Hit dice are one pool. Confirmed.

**Done 2026-11-10** (`PlayState.hitDiceByDie`; Play shows a button per die size when there is more than one; a long rest returns the largest first. The total (`hitDiceUsed`) stays in step for the sheets.)

`PlayState.hitDiceUsed` is one number and `useRests` spends "the largest die". A Fighter 3 / Wizard 2 has 3d10 and
2d6; the app rolls d10 five times.

Fix: `hitDiceUsedByDie?: Record<string, number>` (key "d10"). Spending asks which die when there is more than one
kind. Old saves: spread `hitDiceUsed` over the dice, largest first. The rest functions of R2 restore largest first
(2014: the player chooses; largest first is the sensible default).

### R4. A level can give zero or negative hit points. Verify first.

**Done 2026-11-10** (both Player's Handbooks say "minimum of 1"; the engine and the rules check each floor a level at 1, written apart; test in hpRolls.test.ts. Plutonium not consulted for this one: the books are explicit.)

`engine.ts` `baseHitPoints`: `(roll ?? average) + conMod` with no floor. A Wizard with Constitution 3 (modifier -4)
who rolls a 1 gets -3 for that level. Both rule books say a level gives at least 1. Check Plutonium's handling, then
`Math.max(1, ...)` per level. Test in `hpRolls.test.ts`. Check that the rules check's independent hit point formula
agrees (it must have the same floor, written separately).

### R5. A cycle between statistics caches a wrong value. Confirmed by reading; build the test first.

**Done 2026-11-10** (a statistic in a loop has one value, the one worked out starting from itself; statCycle.test.ts asks in every order. The loop is named in the resolver's findings. 1,200 random characters on the three content sets have no loop today, so no real character changes.)

`stats.ts` `StatBook.get`: when `a` needs `b` and `b` needs `a`, the inner read of `a` returns 0 (the `busy` guard),
`b` is computed with that 0 **and cached**, then `a` is computed from it. Which of the two is right depends on which
was asked first, so two screens can show different numbers for the same character, and determinism (P8) is broken
for such content.

Fix: count cycle hits. `get` keeps a depth counter and a `cut` flag; a value computed while `cut` was set below it is
returned but not cached, except at depth 0. Report each cycle once through a `cycles: Set<string>` that
`resolveTimeline` adds to its findings ("Statistics refer to each other: a, b"). Test: two contributions referring
to each other give the same values whichever is read first.

### R6. The timeline cache does not record everything a level read. Verify first.

**Guard in place 2026-11-10** (src/engine/cache.test.ts: 1,800 edits on SRD characters, a kept resolve equals a fresh one every time; `clearTimelineCache` exported. Not reproduced with today's keys. The old position keys are not exercised by it: part 1 stays open, with E1.)

`timeline.ts` `settleCached` keys an entry by the character without its picks, plus the picks of the slots in the
*final* walk (`pass.rawSlots`). But `walk` also reads: old position keys (`<id>|<n>`), other positions through
`movedLegacy`, and slots that were open in an earlier walk of the same level and closed in the last. A change to one
of those can return a stale level.

Fix, in two parts:
1. Make it exact: `walk` takes a `read(key): string[] | undefined` function instead of touching `ch.selections`; the
   timeline passes one that records every key read (including misses). `used` is that record.
2. Guard: export `clearTimelineCache(reg)`. A property test (`src/engine/cache.test.ts`): for 300 random SRD
   characters, apply 20 random single edits each (change a pick, add a level, equip an item); after every edit the
   cached `resolve` must equal a resolve with the cache cleared (compare ids, stats, slot keys and chosen).

Better still, remove the legacy reads from `walk` altogether: see E1.

### R7. Slot rows on lines that are not a class's. Verify first.

`sheet.ts` `buildCasting`: `const total = useShared && !isPact ? sharedRow[n - 1] : ...` runs for every
spellcasting entry, also a feat's or a species' own entry (`fromClass: false`). A multiclass caster with such an
entry would show the shared slot table on the feat's line too. Test with a Cleric 3 / Wizard 3 who has a feat with
its own spellcasting entry; if it shows, use the shared row only where `fromClass`.

### R8. Armor against a natural armor formula. Verify first, with Plutonium.

`sheet.ts` `buildAc`: with body armor equipped, the armor's number is used and "ac:calculation" (natural armor,
Unarmored Defense) is ignored. Where the rules let the character use the better of the two while armored (the 2014
Lizardfolk's Natural Armor, the Loxodon, Draconic Resilience does not), the lower number shows. And when two body
armors are equipped the last in the inventory wins, silently.

Fix after checking how Plutonium decides: mark each alternate calculation as "unarmored only" or "any" where the
converter can tell from the text ("while you are not wearing armor"), take the best allowed one, and say which in
`parts`. Add a rules-check finding "Two armors worn". The Tortle finding from 2026-11-10 stays.

### R9. Caster progression by class name. Confirmed.

**No change needed (read 2026-11-10).** The converter already states each class's and subclass's share from 5e.tools' `casterProgression` (fivetools.ts, "Share slots with other classes": the statistic `multiclass:spellcasting:level`), and `multiclassCasterLevel` uses that stated level whenever a caster is not one it knows by name. So a homebrew 5e.tools class is counted from its data. The name table stays because Aurora's stated level rounds the Artificer down; it can go with Aurora at D7. Still worth doing: pass `reg` from `sharedSlotLevel`.

`engine.ts` `multiclassCasterLevel` knows full, half and third casters by name (`FULL_CASTERS`, `HALF_CASTERS`,
"fighter", "rogue"); anything else is guessed from its slot row. `sharedSlotLevel` calls it without the registry, so
it falls back to reading the class name out of the id. Homebrew and third-party classes land in the guess.

Fix: 5e.tools states `casterProgression` on each class and subclass ("full", "1/2", "1/3", "artificer", "pact").
The converter writes it as a setter (`caster progression`); the engine reads the setter and keeps the name table only
as the fallback for content without it. Pass `reg` everywhere. The multiclass audit test must not change.

### R10. Attunement read from prose. Confirmed.

**No change needed (read 2026-11-10).** For 5e.tools items the converter writes `reqAttune` into the rarity setter ("Rare (requires attunement)"), which the engine reads before the description; the prose reader only serves Aurora items and goes with them at D7.

`engine.ts`, the inventory loop: `needsAttune` looks for "requires attunement" in the first 400 characters of the
description. 5e.tools has `reqAttune` as data. Make the converter set `attunement` for every item and read text only
for Aurora content. This is one case of E2 below.

## 3. Engine shape: what "ideal" means here

ENGINE-PLAN.md decided against a rewrite, and that is right: the gates took months to earn. These are the changes
that make the engine simpler and faster without moving its results. Do them one at a time, each behind the parity,
sweep, imports and random-character gates with unchanged counts.

### E1. Upgrade saved picks once, at the door, instead of on every walk

`engine.ts` `walk` carries the whole history of pick keys: `legacy` position keys, `oldFits`, `requiredTakes`,
`movedLegacy`, `legacyOffered`, and `upgradePlusTwo` before every resolve. It is the hardest part of the file to
read, it runs for every choice on every walk, and it is why R6 exists.

Change: a function `upgradeSelections(ch, reg): { ch: Character; moved: string[] }` in a new
`src/engine/selections.ts` that does all of it once: for every element with choices, compute what `walk` would read
today for each choice, and write it under the stable key; apply `upgradePlusTwo`; drop position keys it has
resolved; keep the ones it could not place under a `legacySelections` field so nothing is thrown away. Run it when a
character is opened and the registry is ready (where `withGrantedItems` runs), save the result, and note it in the
older-build notice. Then delete the legacy branches from `walk`.

Proof: before deleting anything, a test over the import corpus, the user library copy (`node_modules/.userlib.json`
when present), `legacyKeys.test.ts` and 2,000 random characters with keys rewritten to the old forms: the resolve of
the upgraded character equals today's resolve of the original (ids, stats, slots, chosen). Only then remove the old
code, in its own commit.

### E2. One list of every rule read from prose

With D7 the mechanics Aurora carried as data come from 5e.tools' data or from text. Text readers are spread over
`textMechanics.ts`, `sheet.ts` (`abilityOf` in `buildCasting`, `weaponAbilityOptions`, `withSenses`, `sheetText`),
`engine.ts` (`needsAttune`), `rulesCheck.ts` (`noBodyArmor`, repeatable feats), `fivetools.ts` (`schoolLimit`,
`textProficiencies`, `castableSpells`) and the starting equipment reader.

Make `docs/audit/text-rules.md`: one row per reader with the pattern, what it decides, how many loaded elements it
fires on (a small script over the 5e.tools set), and whether 5e.tools has the same fact as data (item `reqAttune`,
`casterProgression`, `additionalSpells`, `resist`, `senses`, feat `repeatable`, Foundry activities). Then, reader by
reader: data first, text only as the fallback, and a gate that lists every element where the two disagree. The
readers that fire on nothing can go.

### E3. Contributions know which element they came from

`stats.add(name, { ..., from: el.name })` keeps only a name. Two things fall out of an id:
- "Why is this 17?" on every number (the `parts()` function exists) with a link to the element. **For Chris** as a
  feature; the data change itself is safe to make now.
- Tests and reports that do not break when a feature is renamed.

Add `fromId` beside `from` everywhere a contribution is added.

### E4. Do the heavy work off the main thread

`useContent.ts` `rebuild` parses, converts and builds the registry on the main thread: 1.3 s normally and 8 to 10 s
when the 5e.tools data is converted again (C1.7's measurement). The window is frozen for that time.

Change: a Web Worker (`src/aurora/contentWorker.ts`; the CSP already allows `worker-src 'self' blob:`) that does the
reading, parsing and converting and posts back the plain element arrays, with progress messages; the main thread
only builds the `ARegistry` from them. Elements are plain data, so they cross as they are. Keep a synchronous path
for tests. Measure before and after with the launch log. Later the same worker can take the PDF export.

### E5. Stop resolving the character when only play state changed

**Measured 2026-11-10** (5e.tools content, 60 random level-20 characters): a resolve with nothing kept takes 6 to 7 ms, one after a play-state change 2.5 ms. The engine is not what a player waits for; step 4 is done (one context per element, about 8% off), steps 1 and 3 are not worth their risk. What is left of this item is step 2, the screens re-drawing, to be measured in the React profiler first.

`App.tsx`: `r = useMemo(() => resolve(character, content.reg), [character, content.reg])`. Ticking a spell slot,
typing a note or changing hit points makes a new `character`, so the engine, the sheet and every screen run again.
The timeline cache makes the engine cheap, but each level still serialises the whole character (inventory, journal,
companions) for its cache key, 20 times for a level 20 character, and every tab re-renders (no component in
`src/ui` is memoised).

Steps, measuring with the React profiler after each:
1. A `buildPart(character)` that returns the same object while nothing but `play`, `info`, `notes`, `journal`,
   `portrait`, `favorites`, `resources` changed (compare the other fields by reference). Resolve from that.
   `Resolved.character` then lacks fresh play state, so first move the two places in `sheet.ts` that read
   `ch.play` (`slotsUsed` in `buildCasting`) out of `buildSheet` into a small `withPlay(sheet, play)` step.
2. `React.memo` on the tab components; `set` is already stable.
3. The cache key in `settleCached`: build it from the build part's fields once per resolve, not `JSON.stringify` of
   the character per level.
4. Hoist `makeCtx` in `walk`: it is created once per *rule* today, and each call joins the whole inventory into a
   string to check the equipped cache. Once per element is enough (same arguments).

### E6. The portrait out of the character record

`Character.portrait` is a data URL inside the record. It rides along in every autosave, every `localStorage` write
(which then fails and falls back to "id only"), every backup and every bug report (already left out by hand). Move
it to its own store keyed by character id (`portraits`, database version 8, only adding a store), keep reading the
old field, and write the backup format with portraits as an optional part.
